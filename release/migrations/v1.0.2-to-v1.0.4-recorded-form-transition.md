# Provider v1.0.2 recorded Forms with provider v1.0.4

Provider `v1.0.4` is a maintenance candidate for existing provider-v1 state.
It is not published merely because this guide and source descriptor exist.
Verify the canonical Terraform Registry version endpoint and the signed
release before changing a production provider constraint.

Provider `v1.0.2` state may record these exact identities:

- `RelationalDatabase@2.0.0`, schema
  `sha256:3898f8ee507bcebd9e03e80fbc1931b67b477299b1ebe2ff395facb7acf018de`,
  package
  `sha256:dc131e4858ddedbb84d553fdf7808c55fc898a37f15d84839e414fe3ca57c910`;
- `EdgeWorker@3.0.0`, schema
  `sha256:c7fb07db10c937fd6ab119b192552ac239cbcad45dcc12bccd7993decffd2781`,
  package
  `sha256:f03ede50c6b04459e669ed7aaef3e63397b127882a6b4b19dad45ea2da232381`.

Provider `v1.0.4` retains those exact closed codecs. Read, ordinary Update, and
Delete use the complete identity recorded in state, not the newest Form with a
matching kind. Missing or unknown identity fields fail before a Resource host
request. Do not edit these computed state attributes.

## Explicit RelationalDatabase transition

DB2 remains DB2 during an ordinary update. To request the one supported
same-resource transition, configure the DB3 schema bundle and the exact marker:

```hcl
resource "takoform_relational_database" "app" {
  name            = "app"
  engine          = "postgres"
  storage_gib     = 24
  schema_url      = "https://artifacts.example.com/app/schema.json"
  schema_sha256   = "<64 lowercase hexadecimal SHA-256 characters>"
  schema_format   = "takosumi.resource-migrations"
  form_transition = "relational-database-v2-to-v3"
}
```

The configured host must advertise `features.resource_form_transition`. The
provider resolves the marker to its compiled exact DB2 and DB3 Form references;
the user never supplies identity digests. The host operation atomically applies
the desired DB3 spec while preserving the Resource and native identity. State
continues to record DB2 until the host returns exact committed readback and
proof for that same operation, request, spec, revision, and native identity.

Every later apply first reads the deterministic operation. Exact absence, or
an exact same-operation/same-request `prepared` result that explicitly proves
`dispatchAttempted: false`, permits one POST; the host uses a compare-and-swap
so only one caller can begin dispatch. Prepared state with an attempted or
missing flag, indeterminate state, a digest mismatch, or GET uncertainty is
readback-only. If a POST response is lost, the provider performs one operation
GET and never blindly repeats the mutation in that invocation. Preserve the
prior state and rerun the same configuration to reconcile; do not create a new
operation by editing state. A definitive failed operation requires a reviewed
change that produces a new resource revision and request.

Keeping `form_transition` after a proved DB3 commit is safe and does not
retrigger it. A fresh create always uses current DB3 and treats the marker as
an inert declaration. Removing the marker after state records DB3 also leaves
ordinary DB3 lifecycle behavior.

## EdgeWorker stays on its recorded identity

There is no EdgeWorker transition marker. Updating `artifact_url`,
`artifact_sha256`, or `artifact_media_type` for state that records Edge3 sends
an ordinary Edge3 update. It does not change state to Edge4, and the Edge4-only
`assets_path` and `assets_not_found_handling` fields are rejected for recorded
Edge3 state. Provider validation loads the byte-exact published Edge3 Form
Definition, including its historical artifact URL pattern; it is not rebuilt
by subtracting fields from Edge4. A fresh EdgeWorker create uses current Edge4.

## Rollback and recovery boundary

Before changing the provider constraint, retain a backend-supported Terraform
or OpenTofu state backup and the host's database recovery evidence. Reverting
the provider binary cannot reverse a committed database schema/data migration.
If the transition is indeterminate, do not restore or edit state solely to make
the plan green; reconcile the exact operation with the host first. A committed
transition is forward-repaired under DB3 or restored using the owning
host/backend recovery procedure.
